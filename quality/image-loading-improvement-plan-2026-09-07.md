# 画像表示遅延の改善案

2026-09-07 / 対象Git `3c3146d9b6fffb58103cbb0f537272fd680bb5c3`

実施承認後の変更・検証結果は[改善実施記録](image-loading-implementation-2026-09-07.md)を参照。以下は実施前の判断記録。

## 1. 再確認の結果と位置付け

今回は製品ソース、Coil 3.6.2・Ktor 3.5.2・OkHttp 5.3.2の依存ソース、保存済みの実機ログとNativeテストXMLを照合した。新たな実機計測や製品修正は実施していない。基準Gitからの追跡対象ソース差分はない。

| 結論 | 根拠 | 適用範囲 |
| --- | --- | --- |
| 古い接続の復旧待ちが実測した約4.5秒の遅延を作る | Android実サービスログ、固定切断条件での比較 | Androidで直接確認。全ての遅延の原因とは断定しない |
| iOSのソケット設定が後から75秒へ上書きされる | 設定適用順と1秒/3秒の対照試験 | 現行Darwinをシミュレータで確認。実機での発生頻度は未確認 |
| 先読みが残ると表示画像を待たせる | 同一ホストの保留取得をAndroidで5件、iOSで6件作成 | 両OS。通常スクロールでの発生頻度は未測定 |
| 503でも別拡張子を試し、1回の画像取得失敗が12要求になる | 両OSの実Coil＋HTTP | /src/*.jpg、互換画像ポリシー、全候補503という固定条件 |
| 404を保存したキャッシュが自動復旧を妨げる | 両OSで404→サーバー200への切替後も再要求なし | 接続改善とは独立して修正が必要 |

再確認で設計に反映した点は次の3点。

- UIにも500/1,500msの再試行がある。拡張子探索の抑制だけでは多重再試行を解消できない。
- iOSの75秒上書きを削除するだけでは、一般クライアントのソケット待機も実効75秒から設定値45秒へ変わる。
- CoilのDeDupeConcurrentRequestStrategyは、先行取得がキャンセルされると待機側が取得を引き継ぐ。表示中と同じURLの先読みを不用意に止めると、成功途中の通信をやり直す可能性がある。

## 2. 推奨する構成

```
画面の画像要求
  ├─ 表示中の画像
  └─ 管理された先読み（専用の寿命・上限）
        ↓
共有の画像エラー分類・再試行方針
        ↓
既存のCoilメモリ／ディスクキャッシュ
        ↓
画像用通信
  ├─ Android: 一般通信用と独立したOkHttpエンジン
  └─ iOS: 既存Darwinを利用し、画像用HttpTimeoutを正しく適用
```

通常表示・互換表示・カタログのローダーから使う画像用通信の所有者を明確にする。既存の一般画像用／カタログ用キャッシュ領域は維持し、通信エンジンの分離とキャッシュの分離を混同しない。

## 3. 共通: エラー分類と再試行の責任を一本化する

### 変更内容

`ui/image` に画像取得エラーの分類を置き、拡張子フォールバック、サムネイルのUI状態遷移、通信側の再試行が同じ分類を使用する。名称例は `ImageFailureKind` / `ImageRetryPolicy`。HTTP例外のステータスと原因チェーンを確認し、文字列のエラーメッセージに依存しない。

| 結果 | 同じURLの自動再試行 | 別拡張子の探索 | サムネイル→元画像 |
| --- | --- | --- | --- |
| 正常 | なし | なし | 通常の表示仕様に従う |
| 404/410 | UIによる同一URLの即時反復は行わない | 対応済みのソースURL・画像形式に限定して許可 | 既存の有効な元画像URLがあれば一度切替 |
| 503など一時的な5xx | 通信層だけで初回＋最大2再試行。バックオフを維持 | 行わない | 通信障害を理由に大きな元画像へ切り替えない |
| 接続切断・一時的な接続失敗 | 通信層で管理。Android内部の接続復旧も利用 | 行わない | 同上 |
| 401/403 | 自動反復を行わず、実際の失敗を表示 | 行わない | 認証エラーを迂回する切替は行わない |
| 429 | 無条件の即時反復はしない。Retry-After対応を明示して設計 | 行わない | 行わない |
| キャンセル | 直ちに終了 | 行わない | 行わない |
| TLS検証失敗・不正URL・送信先ポリシー拒否 | 再試行しない | 行わない | 行わない |
| デコード失敗 | 原因を別分類。まず同一データを繰り返さない | 正当な形式補正の既存ケースを確認して限定許可 | 対応形式と既存仕様を確認 |

5xxをすべて恒久的に同じ扱いにするのではなく、最初は現在扱っている一時障害を維持し、501等の恒久的な非対応を別分類する。429対応は新規仕様なので、最初の修正で実装しない場合も「拡張子探索やUI再試行をしない」ことは固定する。

`CompatibilityApp.kt` の `resolveCompatThumbnailFailureAction` 呼出しに分類を渡す。通信層が再試行を終えた同じURLへ、UIがさらに2回の自動再試行を掛けない。ユーザーによる明示的な再読込は新しい操作として残す。通常表示・ギャラリー・ビューアーの同等経路も棚卸しする。

フォールバックの途中で503や通信切断へ変わった場合も、その候補で打ち切る。最初の応答だけの分類では不十分。通信障害を理由に「全拡張子が存在しない」という30秒の探索失敗記録を残したり、既知の正しい拡張子対応を消したりしない。

### 期待効果と上限の解釈

固定条件の「全候補503」は、1回の画像操作で12要求から元URLへの3要求へ減らすことを合格条件とする。UI再試行の上乗せも止める。

ただし、Ktorの初回＋2回は論理的な試行回数。OkHttp内部の接続復旧・リダイレクト・DNSの複数経路まで含めた、全状況のHTTP送信数が必ず3になるとは扱わない。接続枠を3本試すだけで打ち切る実装は、前回の古い接続3本の条件で復旧を再び妨げるため避ける。

通信中の待機、バックオフ、フォールバックを合算した操作時間も計測する。現在の90秒を複数層にまたがる操作全体の上限とは見なさない。全体の時間上限を新設する場合はサムネイルと大きな元画像で分け、遅い正常回線の実測後に決める。

### 副作用と対策

自動試行を減らすと、通信層が打ち切った直後の復旧をUIが拾う機会は減る。正常回線・一時切断・遅い回線を同じ画像で比較し、最終成功率を確認する。実際の失敗表示と手動再読込は残す。

## 4. 共通: エラー応答のキャッシュ方針を変える

### 変更内容

`KtorNetworkFetcherFactory` に画像専用の `CacheStrategy` を注入する。

- 読み込み時、保存済みの正常応答は既存と同じ扱いで利用する。
- 保存済みの4xx/5xxを画像本体として返さず、`CacheStrategy.ReadResult(networkRequest)` で再取得へ進める。
- 書き込み時、4xx/5xxは `WriteResult.DISABLED` とする。正常応答と正常キャッシュに対する304更新は既存処理を維持する。
- 既存キャッシュのメタデータに残る404も読み込み時に判定する。新しく404を書かない変更だけでは不十分。
- 正常化した同じURLは再取得後に正常キャッシュで置き換える。読み込み中スナップショットを外部から強制削除しない。
- メタデータなしで保存された既存ローカル画像や、画像ファイル直接読み込みを壊さない。

Coilの既定キャッシュ全体を無効にしたり、全画像を一括削除したりする必要はない。Cache-Control対応ライブラリへの全面移行も、正常画像の再検証頻度が一緒に変わるので今回の第一案にはしない。

### 副作用と対策

存在しないURLへのアクセスが増える可能性がある。上記のUI自動反復停止と一緒に導入する。同じURLの進行中要求はDeDupeで集約し、実測で不足がある場合だけ短いメモリ内の失敗抑制を追加する。永続的な404の代わりに長いTTLを導入して、復旧しない問題を再び作らない。手動再読込はこの抑制を解除できるようにする。

`thumbnailReloadToken != 0L` の間ずっとキャッシュが無効になる既存経路も併せて整理する。手動再読込の対象取得だけを強制更新し、成功後や次の独立した取得では通常キャッシュへ戻す。Compose再構成ごとに再読込が発火しない操作ID・完了状態で管理する。

### 合格条件

404を保存済み→サーバーを200へ変更→自動の新規取得でNETWORK成功→次回はMEMORY/DISK成功。全キャッシュ削除なしで成立すること。真の404、オフライン、手動再読込、同時に同じURLを要求する場合も確認する。

## 5. iOS: 画像用15秒を実効値にする

### 推奨する最小変更

`HttpClientFactory.ios.kt` の `configureRequest { setTimeoutInterval(75.0) }` を削除し、一般クライアントの `HttpTimeout.socketTimeoutMillis` を75,000に明示する。

これにより、一般通信は現在の実効値75秒を維持し、画像用の派生クライアントが設定する15秒をDarwinへ反映できる。要求全体と接続の設定は別項目として扱う。iOSにAndroid向けの新しい再接続機構を追加する必要は、今回の証拠からはない。

ソース内のソケットタイムアウト設定を再検索した結果、共通画像設定以外には別クライアントの `IosArchiveReportSender` がある。この専用クライアントを一般画像修正に巻き込まない。

一般側の設定値45秒が本来の仕様として必要なら、75→45秒への変更は別の振る舞い変更として判断する。今回は画像遅延の修正と分離する。

### 期待効果と副作用

画像が無応答になったとき、意図した15秒のソケット待機が働く。75秒の実測改善値を保証する意味ではなく、既存の1秒/3秒対照試験と設定適用順が根拠。

15秒は画像全体のダウンロード時間ではなく、Darwinでのソケット待機に対応する。少量ずつ届く正常な大画像と、本文の途中で完全に止まる画像を別々に試験する。既存の全体タイムアウトも含めて成功率を確認する。

合格条件は、短縮対照試験でソケット1秒が要求全体3秒より先に発火すること、画像15秒が有効なこと、一般通信の実効値を維持すること。シミュレータに加え、現行ビルドの実機iPhoneで確認する。

## 6. Android: 画像専用の独立エンジンで接続復旧を速める

### 通信構成

一般用途の `createHttpClient()` の再送防止は維持し、画像用に一つの独立したOkHttpエンジンを作る。画像側のみ `retryOnConnectionFailure(true)` を使用する。現在の `httpClient.config { … }` はエンジンを共有するので、これをエンジン分離と見なさない。

`FutachaApplication` が既存の `PersistentCookieStorage` と画像用通信を所有し、MainActivity → FutachaApp → 各ローダーへ注入する構成を推奨する。Activity再生成やモード変更ごとに新しい接続プールを増やさない。単一の画面が共有通信を閉じない所有権にする。Androidの補助プロセスから誤って初期化しない既存条件も維持する。

API例として、一般のHttpClientを公開しない `FutachaImageTransport` を設け、Coil用Fetcherを作る機能と終了処理だけを公開する。BoardRepository、投稿、投票、自動保存へはこのハンドルを渡さない。画像ローダーがHttpClientを所有して閉じる現在の責務は移し替える。

### 必須の条件

- GET/HEADのみ許可。POST等は送信前に拒否。
- 画像URLと送信先を検査し、GETで状態を変える `sd.php` などを通さない。直接URLだけでなく全リダイレクト段階を検査。
- 既存の2chan画像と外部アップローダーのURL形を棚卸しした許可ルールにする。拡張子だけの判定や、二つの禁止パスだけで完全だとは扱わない。署名付きクエリを壊す正規化をしない。
- OkHttp内のリダイレクトを止め、KtorのCookie処理を経由させる。移動先ごとにCookieを選別し、途中のSet-Cookieを保存する。
- 拒否例外、キャンセル、TLS検証失敗を再試行しない。
- 既存Cookieストアを共有し、Coilの正常画像キャッシュキーを維持する。
- `MainThreadSafeResponseCloseInterceptor` を画像側にも適用。共通化する場合は、その挙動を保つ。
- 接続プールの数、実行中Call、待機Call、終了処理を管理する。最初からプール保持1秒や同時通信数増加を組み合わせない。

### 期待効果と副作用

固定試験の4.06〜4.94秒の失敗を、試作では44〜56msの成功に変えられた。これは同じ固定切断条件での効果であり、実サービスの全画像が常にこの時間で出る保証ではない。

副作用は追加の接続プール、正常な外部URLを制限しすぎる可能性、Cookie処理変更。アプリ内で一つに共有し、URL互換性・302/307/308・クロスホスト・キャンセル・ライフサイクルを試験する。接続を短命にして毎回TLSを張り直す案は、通信量・電池・遅延の追加評価が必要なので第一案にしない。

合格条件は、古い接続3本の固定試験で秒単位のKtorバックオフを挟まず成功し、ローカル試験で通常POSTは1回以下、画像側POSTと状態更新先への到達は0回であること。

## 7. 共通: 先読みの寿命と本数を管理する

`CompatibilitySecondaryScreens.kt` のenqueueしたDisposableを、ページ変更で破棄される一時的な配列ではなく、URL単位で管理するCoordinatorへ移す。

- 保持する候補は現在ページの前後。ページ変更時は集合の差分だけを追加・停止する。
- 表示中のURLと同じ取得は、先読みから表示用途へ引き継ぐ。先読みの都合でキャンセルしない。
- ビューアー終了・先読みOFF・Wi-Fi条件不成立で、不要になった取得と待機要求を解除する。
- 最初の調整値として、先読みの同時実行は共有ローダー群で1件、待機候補は前後2件まで。表示画像にはこの先読み枠を適用しない。数値は未実装の初期案で、測定後に調整する。
- 現在の表示・引用・ギャラリーなど別の利用者がいる取得は、参照数で保護する。URLに加え要求サイズ・キャッシュキーを扱い、ネットワーク取得の共有とサイズ別のデコード要求を混同しない。キャンセル後のDeDupeによる再取得も試験し、エラー表示や二重ダウンロードを増やさない。
- NORMAL時の全画像に一律のゲートを追加しない。特にメモリ／ディスクキャッシュの取得まで通信待ちに巻き込まない。

期待効果は、画面外の先読みが5/6件の通信枠を占め続ける状況の解消。副作用は、速い回線で連続スワイプした場合の先読み量が減ること。前後の移動・高速スワイプ・戻る操作で、表示までの時間と通信量を比較する。

初回修正では先読みする画像サイズ・サムネイルか元画像かを同時に変えない。元画像を先読みする仕様へ変えると通信量が増えるため、別の改善として評価する。

## 8. 実装単位と検証順序

| 段階 | 主な変更箇所 | 完了条件 |
| --- | --- | --- |
| 1: 共通エラー処理 | ImageLoaderProvider、CompatThumbnailRetrySupport、CompatibilityApp、新しいエラー分類／CacheStrategy | 全候補503が3要求で終了、UI上乗せなし。保存済み404から復旧。正当な拡張子補正を維持 |
| 2: iOSタイムアウト | HttpClientFactory.ios、画像クライアントの設定テスト | 画像用ソケット設定が有効。一般通信の実効待機を維持 |
| 3: Android通信 | 新しい画像Transport、Androidファクトリ、FutachaApplication、MainActivity、FutachaApp、ImageLoaderProvider | 古い接続から即時復旧。投稿・Cookie・リダイレクト・資源管理の契約を通過 |
| 4: 先読み管理 | CompatibilitySecondaryScreens、共有Coordinator、画像要求の用途・所有権 | 画面外の滞留解消。同一URLの表示への引継ぎが成功 |
| 5: 統合確認 | 両表示モード、カタログ、スレッド、引用、ギャラリー、ビューアー | 両OSの実機で改善と既存機能の維持を確認 |

これは切り分け可能な変更単位。優先度が低いからAndroidを後回しにする意味ではなく、共有エラー処理を整えてからエンジン変更の効果を測りやすくする順序。

診断テストは望ましくない現状をassertしているものがあるため、そのまま製品テストへ移さない。例えば「404後に再取得しない」を「復旧後に再取得して成功する」へ変え、正しい振る舞いを回帰契約にする。

### 実機検証の条件

- 既存調査相当の1,000レス・約200画像の固定データと、その時点で生存している実スレッドを使用。
- 最初の表示、通常スクロール、35秒程度の停止後の再開、先頭へ戻る、連続ビューアースワイプと終了を分ける。
- コールドキャッシュ／ウォームキャッシュ、Wi-Fi／携帯回線、低速だが正常な応答／途中停止、HTTP/1.1／実サービスのTLS等を分ける。
- 計測を「要求待機・接続・応答待ち・本文受信・デコード・UI反映」に分け、中央値・p95・p99・1秒/3秒超の件数・失敗率・転送量を記録。平均値だけで判定しない。
- キャンセル後のCall・接続数、画面往復後の保持メモリを確認。デバッグ計測の負荷を考慮して同じ条件の変更前後を比較する。
- Android実機に加え、現行ビルドの実機iPhoneを必須にする。既存9.6のiPhoneログを現行版の改善証拠に使わない。

まず対象の共通／Android／iOSテストと端末試験を実行し、実装が揃った段階でプロジェクトのqualityGate・品質契約を確認する。固定サーバーで速くなっただけで、製品UIの確認を完了としない。

| 2. iOS/NSURLSession | タイムアウト上書き修正に賛成 | 上書きだけ削除すると一般通信の実効待機が75→45秒になる。画像15秒への変更も無応答に近い遅い回線で失敗を早める | 一般側の実効75秒を設定として維持。低速連続受信と完全停止を分け、現行版実機iPhoneで確認 |
| 3. KMP・資源管理 | アプリ単位の所有権を条件に賛成 | Activity再生成・モード変更でクライアントを増やす、ローダー破棄で他の画面が使う通信を閉じる | 生成・終了の責務を一か所へ。画面往復・バックグラウンド復帰・プロファイル切替後の数と動作を確認 |
| 4. キャッシュ設計 | 404の読み出し方針変更に賛成 | エラーを保存しなくなると消えた画像へ繰り返しアクセスしやすい。新規保存だけ禁止しても既存404は残る | UI反復の整理と同時導入。既存404→200、真の404、オフライン、手動更新を検証。正常画像は保持 |
| 5. サーバー負荷・再試行 | 多重再試行の削減に賛成 | 試行削減は障害直後の復旧を拾う機会も減らす。即時再試行を大量同時発生させると負荷が集中 | バックオフ・ジッター・Retry-Afterを考慮。最終成功率と到達回数を同時に評価 |
| 6. セキュリティ・認証 | 送信先とリダイレクト管理を必須と判断 | GET限定でも状態更新が可能。既存Android設定はCookieを別ホストへ転送するケースがある。厳しいURL制限は正常な画像を拒否し得る | 各移動先の検査、Cookieの再選別、署名付きURLを保つ。実際の対応アップローダーで確認 |
| 7. Compose・表示体験 | 先読み寿命の管理に賛成、一律停止は要注意 | 表示中と同じ画像の先読みを止めるとダウンロードがやり直され得る。先読み1件制限は連続スワイプの先回り量を減らす | 表示への所有権引継ぎ。URLだけでなく要求サイズ・キャッシュキーを考慮し、同じ取得と異なるデコード要求を区別 |
| 8. メモリ・電池・性能 | 通信枠の増加より不要取得の削減を優先 | 別プールの常駐、短すぎる接続保持、取得完了後のデコード集中がメモリ・TLS通信・電池消費を増やす | 最初は接続本数やキャッシュ容量を増やさない。低メモリ端末と長時間利用でピーク・残留を測る |
| 9. 互換性・回帰試験 | エラー種別による制限に条件付きで賛成 | フォールバックの停止範囲が広いと、本当に拡張子が違う画像やサムネイルが消えた元画像を表示できなくなる | 404→正しい別拡張子、サムネなし→元画像、あぷ小、静止画/GIF/動画、引用・ギャラリーの契約を維持 |
| 10. リリース・観測 | 段階導入を推奨 | 複数変更を同時に出すと効果や悪化の原因を特定しにくい。詳細ログは処理負荷とURL情報の露出を増やす | 変更単位ごとの比較と戻せる境界。計測は識別子・区間時間・ステータス中心、Cookie等を記録しない |

### このレビューを反映した採用判断

共通エラー処理とキャッシュ方針、iOSのタイムアウト整備を先に実施する。Androidの独立エンジンは投稿・Cookie・リダイレクト・寿命の試験を満たして導入。先読み上限1件は仮設定として扱い、連続スワイプの表示時間と不要通信の減少を比較して決定する。

全クライアントの即時再接続ON、全キャッシュ削除、無条件の並列度増加、全画面の一律短時間タイムアウトは採用しない。
