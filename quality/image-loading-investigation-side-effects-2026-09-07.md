# 画像遅延・第4回調査: 高速化案の副作用とリダイレクト

2026-09-07 / Android SCG33・Android 16 / Git `3c3146d9b6fffb58103cbb0f537272fd680bb5c3`。

## 結論

前回の「古い接続からの復旧を、画像専用の独立エンジンで速める」方針は引き続き有力。ただし、**エンジンを分離するだけでは不十分。Cookie とリダイレクトの扱い、画像以外の操作を通さない設計が必要**。

今回、永続Cookieの共有、Coilキャッシュの継続、キャンセルと終了時の接続解放、503の待機付き再試行を実機で確認した。一方、現行クライアントにもあるリダイレクトの問題を新たに再現した。これは元の画像遅延の直接原因を示すものではなく、修正時に維持・改善すべき通信挙動の発見。

## 1. 実機試験の条件と結果

一時的な `ImageSideEffectInvestigationTest` を端末上で実行。全通信は端末内のHTTPサーバー（127.0.0.1 / localhost）、Cookieは試験専用の値・保存ディレクトリ。実サービスへの投稿・投票は行っていない。

独立エンジンの試作は、OkHttp即時再接続、GET/HEAD制限、Ktor最大2回の再試行・指数バックオフ、画像用90/15/15秒タイムアウトを使用。実際の `MainThreadSafeResponseCloseInterceptor` を再利用した。アプリ全画面への製品配線は未実施。

| 確認項目 | 観測結果 |
| --- | --- |
| 永続Cookie共有 | 通常側が取得したCookieを画像側へ送信、画像側の更新を通常側へ反映。Secure CookieはHTTPへ送らない。保存ファイルからの復元も成功 |
| クライアントの独立性 | 画像側をcloseしても通常側の取得・Cookie利用は継続 |
| 実際のCoil画像取得 | NETWORK → MEMORY_CACHE → DISK → 新しいクライアント・ローダーでDISK。サーバーへの画像要求は合計1回 |
| メインスレッドからのキャンセル | 10回。サーバー要求10回、キャンセル後にクライアントを閉じる前から実行中・待機中のOkHttp Callは0 |
| 終了時の接続解放 | 上記10サイクルそれぞれでclient.close後のプール接続数0 |
| 継続的な503 + Retry-After: 2 | 合計3要求、4,747ms。待機を保って打ち切る |
| 404へのHTTP再試行 | 要求1回。以前確認したCoilの404キャッシュ問題は別途残る |

最初の5テストは8.272秒で成功。永続Cookieのリダイレクトを追加した1テストは0.726秒で成功。キャンセル後のCall解放を「client.close前」にも厳密化した再試験は2.110秒で成功。計6種類のテストを実行した。

キャンセル試験は各回でローダーとクライアントを生成・終了する資源管理試験であり、アプリ全体の長時間メモリ・電池消費やTLS切断の網羅試験ではない。最初の試験と厳密化後の試験を合わせ20回キャンセルしたが、上表は厳密化後の10回の結果。

## 2. 新発見: 現行設定でもリダイレクト時のCookie処理に問題

`127.0.0.1` にだけ有効なダミーCookieを保存し、`localhost` への302を返した。別途、同一ホストの302レスポンスに新しい `Set-Cookie` を付け、移動先への送信と保存を調べた。

| 構成 | 別ホストへ元のCookieを転送 | 302途中のCookie更新を保存・送信 |
| --- | --- | --- |
| 現行の createHttpClient | する | しない |
| 独立した画像クライアント、OkHttpがリダイレクト | する | しない |
| 独立した画像クライアント、Ktorがリダイレクト | しない | する |

最初に `AcceptAllCookiesStorage` で別ホスト転送を観測し、その後、実アプリの **`PersistentCookieStorage` でも上表の3構成を直接比較して再現**した。localhost向けのCookieを新規発行した試験ではない。元のホストにのみ有効なCookieがHTTPヘッダーとして残るかを調べている。

### コードと結果の対応

- `shared/src/androidMain/kotlin/network/HttpClientFactory.android.kt` はOkHttpの `followRedirects(true)` とKtorの `HttpCookies` を併用している。
- 同プロジェクトの依存ソース（OkHttp 5.3.2 `RetryAndFollowUpInterceptor.kt`）では、別ホストへの移動時に `Authorization` は除去するが、明示的に付いた `Cookie` ヘッダーはこの処理で除去しない。
- Ktor 3.5.2 `HttpCookies.kt` はsend/receiveパイプラインで送信先に合うCookieの選別・応答Cookie保存を行う。OkHttp内部で追従すると、このKtor処理を移動の各段階で通らない。
- 試作の `engine { config { followRedirects(false) } }` でOkHttp内部の追従を止め、Ktorのリダイレクト処理を使うと、今回の別ホスト転送と途中Cookie更新欠落を回避できた。

これは高速化変更によって初めて生じる副作用ではなく、現行構成をそのまま独立エンジンへコピーすると引き継いでしまう問題。実サービスでのCookie流出や認証失敗が起きた事実を確認したものではない。今回の通信は全て端末内のダミーCookie。

製品修正では画像側に限定してリダイレクト処理を検討する。一般クライアント全体への変更は、投稿時の302/307/308等の扱いにも関係するため、この試験結果だけで安全とは判断しない。

## 3. GET/HEAD制限だけでは状態更新を防げない

`HttpBoardApi.kt:235` の「そうだね」は `sd.php` へのGETで状態を更新する。

ダミーサーバーで確認したところ、GET/HEAD制限だけの試作は、直接 `/sd.php` を開く場合も、画像らしい `/redirect.jpg` からそこへ302移動する場合も通す。ダミー状態更新先への到達は計2回。

各HTTP送信直前のネットワークInterceptorでパスを検査する試作では、直接・リダイレクト経由とも到達を防げた。追加の状態更新先要求は0回、302を返す元URLへの要求は1回。拒否専用例外を再試行対象から外したため、拒否した操作をバックオフ後に繰り返すこともなかった。

ただし、試作は `sd.php` / `del.php` のみを拒否する切り分け用であり、これを完全な画像URL検証と見なさない。製品では次を一緒に満たす必要がある。

- 独立クライアントを画像取得経路にだけ渡し、BoardApi等の投稿・投票経路に渡さない。
- 直接URLに加え、リダイレクトの各送信先にも同じ画像取得ポリシーを適用する。
- 正常な外部アップローダーやサムネイルへの移動を壊さない条件を検証する。

## 4. 改善案の評価を更新

前回の固定切断試験では、現行4.06〜4.94秒で失敗に対し、独立エンジンの即時再接続は44〜56msで成功している。今回の検証により、この案がCookie・画像キャッシュを必ず捨てるわけではなく、適切な共有と終了処理で維持できることが分かった。

製品実装の条件は、画像専用の独立エンジンを再利用し、既存Cookieストア・Coilキャッシュ・キャンセル時の応答クローズ処理を維持すること。加えて、リダイレクト処理をKtor側で扱い、状態更新先を含む画像以外への到達を防ぐ設計が必要になる。

503の2回再試行と待機は実測で維持できた。ただし、OkHttp内部の復旧、Ktor、UI、拡張子フォールバックを合算した全パターンの最大送信回数までは今回検証していない。

残る検証は、製品UIへの配線後の実サービスの画像・外部アップローダー・リダイレクト互換性、複数ローダー共有時の長時間資源消費、TLSでのキャンセル、iOSのDarwin経路。今回のAndroid/HTTP試験だけで「副作用なし」とは結論しない。
