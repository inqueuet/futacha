# 長いスレッドの画像遅延・追加調査

> [第3回調査](image-loading-investigation-controlled-2026-09-07.md)で、実機内の固定した切断条件による再現と、GET専用の即時再接続・POST拒否の試作検証まで完了した。

2026-09-07 / Android SCG33、Android 16、ふたちゃ10.4 / 167、としあき（仮）モード。
対象ソース: `3c3146d9b6fffb58103cbb0f537272fd680bb5c3` に一時的な計測コードを追加。

## 判明した原因

**有効でなくなったHTTP/1.1接続を再利用し、その失敗に対して秒単位の再試行待ちを挟むことが、実際の画像遅延を引き起こしていた。**

初回調査では失敗理由が不明だった。今回はCoilのEventListenerとOkHttpのEventListenerで通信・デコード・キャッシュを分離し、同種の遅延を約4.54秒で再現できた。最初の3回は異なる既存接続で応答ヘッダーを受け取れず、4回目に新しい接続を作ると成功した。

前回の約7.3秒の事象そのものには詳細ログがないため、それも完全に同じ原因だったとは断定しない。今回の4.54秒の事象については、エラーから成功まで各段階を追えている。

## 実際の時系列

対象スレッド: `https://may.2chan.net/b/res/1433132557.htm`（先のHTML取得時1000レス、サムネイル183件）。先頭から65回スクロールし、40回戻り、末尾へ移動した。

対象画像: `/b/thumb/1788741558735s.jpg`（8,950 bytes）。

| 時刻 | イベント | 計測結果 |
| --- | --- | --- |
| 09:51:27.068 | Coil画像読込開始 | メモリ状態NORMAL |
| 09:51:27.075〜.081 | 既存接続197137032でGET | 6msで `unexpected end of stream` |
| 09:51:28.123〜.127 | 再試行、既存接続204525792 | 4msで同じエラー |
| 09:51:30.762〜.770 | 再試行、既存接続185580517 | 9msで同じエラー |
| 09:51:30.786 | CoilがErrorを返す | 3717ms経過、デコード未開始 |
| 09:51:31.322 | 本文UIが再試行 | 失敗表示ログから約515ms後 |
| 09:51:31.345〜.550 | 新規接続121539255でGET | HTTP 200、転送完了205ms |
| 09:51:31.576〜.582相当 | デコード | 6ms（EventListenerの相対時刻から算出） |
| 09:51:31.585 | Coil成功 | 再試行開始から263ms |
| 09:51:31.609 | 本文の成功ログ | 最初の開始から約4.54秒 |

3本の失敗した接続は、それぞれ約35秒、43秒、55秒前にも同じ接続IDで利用されていた。失敗する試行ではDNSやTCP接続をやり直しておらず、接続取得から数msでヘッダー読込がEOFになっていた。新規接続の試行だけDNS・接続イベントが現れ、成功した。

3回のHTTP失敗そのものは計19ms程度。最初の2回の失敗後に約1042msと2635msの待機があり、さらにUI側の約500ms待機が加わっている。**この画像では転送やデコードより、失敗間の待ち時間が大きい。**

どこが接続を切ったか（配信サーバー、途中のネットワーク機器など）はパケットキャプチャで検証していない。観測で確定できるのは、古い接続でヘッダー受信前にEOFになり、新規接続で成功すること。

## なぜこの動作になるか

`shared/src/androidMain/kotlin/network/HttpClientFactory.android.kt`:

- アイドル接続を最大5本、5分保持する設定。
- `retryOnConnectionFailure(false)` を指定。コメントではPOSTの意図しない再送防止が理由。
- Ktorの `HttpRequestRetry` は対象GETの例外等を最大2回再試行し、`exponentialDelay()` を使用。

ローカルにある実際の依存ソースも確認した。

- **OkHttp 5.3.2**: `RealRoutePlanner` はGETに対する `doExtensiveHealthChecks` をfalseにする。`RealConnection.isHealthy` の追加のソケット健全性確認はこのフラグが必要。単にプールに存在することは、その接続で次の応答を受信できる保証にならない。
- **Ktor 3.5.2**: `exponentialDelay()` の初回は1000ms＋0〜999ms、2回目は2000ms＋0〜999ms。今回の約1042ms、2635msと一致する。
- **アプリの本文**: `CompatThumbnailRetry.kt` はさらに500ms / 1500ms待機して再試行する。

長いスレッドで本文を読んだり、キャッシュ済み画像を戻って見たりしている間は画像通信が止まる。その後に未取得の画像へ進むと、古い接続を使う条件が生まれる。これは今回の操作と整合する説明であり、「画像が多いほどデコードが一律に遅くなる」という証拠は得られなかった。

## 計測全体

通常設定の一連の計測（起動、65回前進、40回戻る、末尾移動、待機後の追加スクロール）:

| 項目 | 結果 |
| --- | --- |
| Coilリクエスト | 167回: 成功164、キャンセル2、Error 1 |
| 通信から成功した画像 | 105回、Coil所要時間中央値78ms、p95 355ms、最大1714ms |
| メモリキャッシュから成功 | 59回、Coil内の計測はすべて1ms未満 |
| デコード | 105回、中央値4ms、範囲2〜8ms |
| 画像HTTP通信の失敗 | 6回、いずれも応答ヘッダー読込中のEOF |
| メモリ圧迫 | 記録された全イベントでNORMAL、キャッシュ上限64MiBを維持 |

Coilの成功時間の最大1714msには、別の読込で発生した内部通信再試行が含まれる。一度Errorを返してUI側で再試行する場合は別のCoilリクエストになるため、4.54秒という画像表示までの総時間はこの「成功リクエスト最大値」には含まれない。

通常設定でネットワークからの取得が中央値78msだったこと、メモリキャッシュで59回成功していることから、今回の条件で恒常的な帯域不足やキャッシュ全体の無効化を主因とする根拠はない。これを他の回線・画像形式・端末へ一般化はしない。

## 接続保持時間を変えた比較

一時的な比較版では、同じ計測コードを残し、接続プールのアイドル保持時間だけを5分から1秒へ変更した。通信の自動再送設定はfalseのまま。

未取得画像を含む別の長いスレッド `1433132478` を開き、12秒待機→8回スクロールを3回実施した。この時点で:

- 画像27件がすべてNETWORKから成功。
- 所要時間57〜562ms、中央値84ms。
- 画像HTTP接続の失敗0件、CoilのError 0件。

さらに35秒待機してから8回スクロールし、追加4画像も82〜447msで成功、接続エラーなし。比較版の最終集計は31件、すべてNETWORKから成功、57〜562ms・中央値92msだった。キャッシュヒットで速くなった比較ではない。

これは少数の実ネットワーク比較で、同一画像の厳密なベンチマークではない。1秒が製品の最適な保持時間だと結論するものでもない。古い接続を使わない条件で同じタイプの遅延が消えることを確認するための実験。

## 別件: 404応答のキャッシュ再利用

実機で観測したEOFとは別に、**Coil 3.6.2の標準CacheStrategyが404を保存し、以後の自動再試行でもその404を再利用する**問題をJVMの再現テストで確認した。

実際の `NetworkFetcher.Factory`、`DiskCache`、アプリの `createFutachaConcurrentRequestStrategy()` を使用。テスト用NetworkClientは1回目だけ404、2回目以降は200を返す設定にした。

結果:

1. 最初の取得はHTTP 404。
2. キャッシュ有効のまま2回再試行しても404。ネットワーク呼出し回数は1回のまま。
3. ディスクキャッシュを無効にするとネットワークへ到達して200になる。

`ImageCacheInvestigationTest.cached404PreventsAutomaticRetryFromReachingRecoveredServer` が成功。あくまで現在の不都合な挙動を確認する診断テストであり、望ましい仕様を固定する回帰テストではない。テストソースは製品ツリーから外して証跡に保存した。

本文側は500ms / 1500msの待機を追加するため、サーバーが復旧していても元のサムネイルを再取得できず、さらに元画像へフォールバックする条件になる。今回の実機EOFを404が引き起こしたわけではない。

## 修正方針として優先するもの

1. **画像GETの古い接続からの復旧を速くする。** 画像読込専用の接続管理、保持時間、即時再接続を検討する。現在のPOST再送防止を維持した設計が必要。
2. **例外ごとに再試行待ちを分ける。** 数msで検出できる古い接続のEOFに対して、5xx等と同じ秒単位のバックオフを繰り返す必要性を見直す。
3. **画像の404/410を永久に再利用しないキャッシュ方針。** 成功レスポンス中心の保存方針、失敗の期限、必要時の再取得を定義する。UI側のメモリキー変更だけではディスク上の404は回避できない。

前回挙げた「先読み不足」「原寸デコード」「メモリ圧迫」は一般的な候補として残るが、今回再現した秒単位の遅延では、上記の接続管理と再試行が優先。

## 範囲と証跡

- 今回原因を確認したのはAndroidのOkHttp経路。Darwinを使うiOSについて、同じ接続不具合があるとは結論しない。404キャッシュの再現は共通のCoil実装に対するもの。
- 計測コードのログ出力自体に多少の負荷がある。所要時間は製品版の厳密なベンチマークではない。
- 計測・比較用のソース変更と診断テストは `build/image-latency-investigation/phase2/instrumentation/` と `probe-short-pool.patch` に保存し、製品ソースには残さない。
- `live.log`、`short-pool.log`、`default-summary.json`、`cache-test.xml`、各ビルドログ、元APKを同ディレクトリに保存。ログには画像URLが含まれるが、Cookieやヘッダーは記録していない。
- 比較版を製品修正として採用していない。調査後はAndroid実機のAPKも調査前の版へ戻した。
