# 画像遅延・第3回調査: 原因の固定再現と修正方針

2026-09-07 / Android SCG33、Android 16 / Git `3c3146d9b6fffb58103cbb0f537272fd680bb5c3`。

## 結論

**「古い接続の再利用失敗→秒単位の再試行待ち」を、実ネットワークの状態に依存しない条件でも再現した。画像GET/HEAD専用の通信エンジンに即時再接続を持たせる方針が有力。**

実機内のテストサーバーで同じ切断条件を作り、通常設定は4.06〜4.94秒で失敗、即時再接続する読込クライアントは44〜56msで成功した。待機時間だけをゼロにしても取得失敗は解消しなかった。

同時に、共有クライアント全体で即時再接続を有効にすると、ローカルのダミーPOSTが実際に2回処理されることを確認した。読込専用クライアントのPOST拒否も試作し、送信件数0を確認した。

## 1. 固定した条件での実機試験

`ImageConnectionInvestigationTest` を一時的に追加し、Android実機上のInstrumentationとして実行した。通信先はすべて端末内の `127.0.0.1`。ふたばへの投稿は行っていない。

テストサーバーは3つのGETを同時に待ち合わせて、必ず3本のHTTP/1.1接続を確立する。2 bytesの本文と `Connection: keep-alive` を返し、読込完了後にサーバー側から3本を閉じる。その後、同じクライアントでGETを実行して所要時間・失敗・再試行を記録する。

通常設定は実際の `createHttpClient(context)` をそのまま使用。待機ゼロ版もこのクライアントから派生させた。短いプールと即時再接続版はテスト内の試作クライアントを使用した。

最初に3回反復し、POST拒否の試作を加えた最終試験をさらに1回実施。いずれもJUnit結果は `OK (1 test)`。1つのテストメソッド内で複数の比較ケースを順に実行している。

| 条件 | 4回のGET所要時間 | 結果 |
| --- | --- | --- |
| 製品の通常設定 | 4940 / 4064 / 4476 / 4246ms | すべて失敗。Ktor再試行2回を消費 |
| 再試行待ちだけゼロ | 89 / 68 / 78 / 81ms | すべて失敗。再試行2回を消費 |
| アイドル接続保持1秒 | 50 / 47 / 48 / 36ms | すべて成功。Ktor再試行0回 |
| 即時再接続する読込クライアント | 44 / 56 / 56 / 55ms | すべて成功。Ktor再試行0回 |

通常設定・待機ゼロ・即時再接続版では、切断から150ms後に測定を開始した。短いプールの条件だけは、自然な破棄を待つため1250ms後に測定を開始している。この準備待機は表の所要時間に含まない。

失敗した通常設定でも、その次に別のGETを実行すると新しい4本目の接続で40〜49msで成功した。古い接続3本を順に失敗するまで試すことと、その間の待機が問題であることが分かる。

**これはローカルHTTP通信の試験であり、インターネット上の画像が44msで表示できるという意味ではない。** 画像デコードやTLSを含めず、通信復旧の挙動を切り分けたもの。前回の実画像・TLS・Coilの計測を補完する証拠として使う。

## 2. 投稿再送の影響も実測

別のケースでは、サーバーがPOST本文をすべて読んで処理件数を増やした後、応答を返す前に接続を閉じる。同じPOSTを再受信した場合だけ200を返す。

| 条件 | サーバーでのPOST処理件数 | 結果 |
| --- | --- | --- |
| 製品の通常クライアント | 1件 × 4回 | 応答取得失敗を返し、自動再送しない |
| 共有クライアント全体で再接続ON | 2件 × 4回 | クライアントには成功が返るが、POSTは重複 |
| GET/HEAD以外を拒否する読込専用試作 | 0件 × 1回 | 通信前にPOSTを拒否 |

Ktor層で「POSTを再試行しない」と設定していても、下位のOkHttpがPOSTを再送し得ることを確認した。`retryOnConnectionFailure(false)` を一括でtrueへ戻すだけの変更は採用しない方針が妥当。

読込専用の試作は、Ktorのリクエスト処理でGET/HEAD以外を拒否し、独立したOkHttpエンジンでは再接続を有効にした。最終試験では、同じガード付きクライアントが古い接続からのGET復旧に成功し、POSTを通信前に拒否する両方を確認した。

## 3. 配信先の接続保持に関する補助試験

Macから `may.2chan.net` の同じ小さな画像へHTTPS接続し、応答をすべて読んでから一定時間待ち、同じソケットで再取得した。

| 待機時間 | 結果 |
| --- | --- |
| 1 / 3 / 5 / 8 / 15秒 | 同じソケットでHTTP 200 |
| 20 / 25 / 29 / 31 / 33 / 35秒 | 応答前に `RemoteDisconnected` |

初回応答では `Connection: close` や保持期限を伝える `Keep-Alive` ヘッダーは確認できなかった。今回の少数サンプルでは15〜20秒の間に接続が利用できなくなる条件があった。アプリのアイドル保持5分とは大きな差がある。

これはMac側経路の観測であり、配信サーバーの恒久的なタイムアウト設定値や、全回線の挙動を断定するものではない。前回Android実機で約35〜55秒前に使った接続が失敗したこととは整合する。

## 4. 現在の「画像用クライアント」は独立した通信エンジンではない

`shared/src/commonMain/kotlin/ui/image/ImageLoaderProvider.kt:284` は、渡された `httpClient` を `.config { ... }` で画像用に派生させている。

実際に使用中のKtor 3.5.2の `HttpClient.config` 実装は、元の `engine` をそのまま新しいHttpClientへ渡す。**画像用に別のHttpClientオブジェクトを作っていても、通信エンジンは共有している。**

このため、修正では画像読込用の独立したエンジンを用意する必要がある。画像ごとにクライアントを作るのではなく、アプリ内で再利用する。Cookieの永続ストレージ、必要な通信設定、タイムアウト、キャンセル時の応答クローズ処理、終了処理は維持する。今回の試作は輸送層の検証用であり、このアプリへの配線・Cookie共有・ライフサイクルまで実装した製品修正ではない。

## 5. 関連する変更履歴

Git blameと親コミットを確認した。

- `7a5d88b`（2026-08-21）: Androidの `retryOnConnectionFailure(true)` をfalseへ変更。コメントではPOST重複防止が理由。
- `b64a60a`（2026-08-24）: Ktorの最大2回の再試行と `exponentialDelay()` を追加。
- `f94fd63`（2026-08-24）: 上位層で再試行を管理するリクエストを除外する条件を追加。

今の挙動を構成する変更箇所まで追跡できた。ただし、各過去リリースを実機で比較したわけではないので、ユーザーが遅さを感じ始めたバージョンや、初めて問題が発生したリリースは断定しない。

## 6. 修正方針の優先順位

第一候補は、**画像のGET/HEADに限定した独立エンジンで即時再接続を許可し、投稿用クライアントの再送防止を維持する構成**。リクエストメソッドの制限も明示的に持たせる。通常の接続再利用を保ちつつ、死んだ接続を秒単位の待機なしに捨てられる点を固定条件で確認できた。

### 副作用の確認範囲

追試: [第4回・副作用とリダイレクト](image-loading-investigation-side-effects-2026-09-07.md)。以下は第3回時点の範囲。第4回ではCookie共有・キャッシュ・キャンセル等を実機確認し、リダイレクト時の既存Cookie問題を追加で再現した。

試作で確認したのは、固定した切断条件からのGET復旧とPOSTの通信前拒否まで。「副作用なし」を確認した製品実装ではない。

- **GET/HEAD制限だけを安全性の根拠にはしない。** `HttpBoardApi.kt:235` の「そうだね」は `sd.php` へのGETで状態を更新する。専用クライアントは画像取得経路に限定し、BoardApiや投票・投稿等の処理へ渡さない配線が必要。
- 独立エンジンは接続プール等の追加資源を持つ。画像ごと・画面ごとに無制限に生成せず、アプリ内で共有・適切に終了する。通信量、接続本数、長時間利用時の資源増加は試作では未検証。
- 現在の派生クライアントが引き継ぐCookieストア、通信設定、画像キャッシュ、タイムアウト、キャンセル時の後始末を維持する必要がある。新規エンジンを作るだけでは同等になる保証はない。
- 障害時の即時再接続は試行頻度を上げる。サーバーエラー等へのバックオフ、キャンセル、総試行回数の上限を含めた製品経路での検証が必要。

接続保持時間の短縮も有効だったが、1秒という値は原因切り分け用であり最適値ではない。短すぎる値は新規TCP/TLS接続を増やす。待機時間だけの短縮は、今回の3本の古い接続が残る条件では取得成功につながらなかった。

前回確認した404キャッシュの再利用は別件として修正対象に残る。接続復旧の改善だけでは、すでにキャッシュされた404からの復旧は解消しない。

## 範囲と証跡

- AndroidのOkHttp経路に対する結論。iOSのDarwinエンジンについて同じ修正が必要だとは結論しない。
- 製品ソースの通信設定は変更していない。一時的なInstrumentationテストと、ローカルHTTPを許可するDebug専用リソースだけを追加して検証した。
- 調査後はテストとDebug専用リソースを製品ツリーから外し、実機APKを調査前へ戻した。新たに入れたInstrumentationアプリも削除済み。
- `build/image-latency-investigation/phase3/` に `matrix-with-guard.log`、`device-test*.txt`、`server-idle*.json`、テストソース、Debugリソース、ビルドログを保存した。診断テストには現状の失敗や危険な設定での重複を確認するアサーションがあるため、望ましい製品仕様を固定する通常の回帰テストとしては登録しない。
