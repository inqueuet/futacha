# 画像の多い長いスレッドでの表示遅延調査

> 追加調査で、Androidの古いHTTP接続の再利用失敗と再試行待ちを実測できた。[追加調査結果](image-loading-investigation-followup-2026-09-07.md)を参照。以下は初回調査時点の記録。

調査日: 2026-09-07。解析対象: `3c3146d9b6fffb58103cbb0f537272fd680bb5c3`。

## 結論

Android実機で、1000レス・サムネイル205件のスレッドをスクロールし、1枚の画像が最初の試行開始から約7.3秒後に表示される現象を確認した。最初の試行が約4.9秒で失敗し、自動再試行で成功している。通常のサムネイルは数百msであり、今回の条件では画面全体の描画停止より、個別画像の失敗・再試行が目立つ。

ただし、最初の失敗の根本原因は未確定。既存の `CompatThumbnail` ログは例外・HTTPステータス・キャッシュ取得元・通信各段階を記録しておらず、通信、キャッシュ読込、デコードなどを区別できない。「回線だけが原因」「キャッシュが壊れている」とは断定できない。

## Androidの再現手順と結果

対象URL: `https://may.2chan.net/b/res/1433131197.htm`。取得時HTMLは625,805 bytes、サムネイルURLの重複除去後件数は205。としあき（仮）モードの本文画像を対象にした。

1. URLからスレッドを開く。
2. 35回上方向へスワイプして約160番のレスまで進む。
3. 35回逆方向にスワイプして先頭に戻る。
4. 最下部ボタンで末尾に移動し、そこから35回逆方向にスワイプする。

スワイプはAndroidの `input swipe`、250ms、操作間にホスト側で180ms待機。全205画像を漏れなく表示した試験ではない。アプリデータやキャッシュの削除は行っていないため、各画像が完全にコールドだったとは保証しない。

| 操作 | 画像の結果 | 描画時間p99 / Janky frames |
| --- | --- | --- |
| 比較用の短いスレッド | 記録された4画像は206〜367ms | 初回起動等も含むため性能比較から除外 |
| 長いスレッド、先頭から約160番まで | 最初の採取で180ms以上の成功13件、191〜501ms、中央値267ms。採取直後に216msの成功が1件追加 | 34ms / 1 of 2202 |
| 同じ範囲を戻る | 大半は新たな180ms以上の成功ログなし。ただし先頭画像が4883msで失敗し、その後再試行で成功 | 25ms / 1 of 2178 |
| 末尾から戻る | この操作区間の180ms以上の成功16件、187〜382ms | 21ms / 0 of 2240 |

**成功ログは180ms以上の場合だけ出る。上記は全画像の平均・中央値やキャッシュヒット率ではない。** ログの無い画像を、すべてメモリキャッシュヒットだったとは判定できない。gfxinfoも画像単体ではなく操作区間の描画統計。

### 約7.3秒かかった画像

対象: `https://may.2chan.net/b/thumb/1788706492030s.jpg`

```text
09:41:44.563 Failed post=1433131197 attempt=0 elapsedMs=4883
09:41:47.009 Slow load post=1433131197 elapsedMs=1925
```

最初の試行開始の推定時刻は09:41:39.680、次の試行開始は09:41:45.084。失敗から再試行開始まで約521msで、コードの500ms待機と整合する。開始から成功まで約7329ms。これは既存ログのCompose側開始時刻からの推定で、ネットワーク転送時間そのものではない。

同じURLを後からMacで取得するとHTTP 200、約128msだった。画像が恒久的に消えている説明は支持しないが、端末も時刻も異なるのでAndroidの当該試行の通信状況を証明するものではない。

## コードから分かったこと

### 1. 本文の再試行は待ち時間を積み重ねる

- `shared/src/commonMain/kotlin/ui/compat/CompatThumbnailRetry.kt:3`: 本文サムネイルは最大2回再試行し、500ms / 1500ms待つ。その後、元画像へのフォールバックがある。
- `shared/src/commonMain/kotlin/ui/compat/CompatibilityApp.kt:11667`: Error状態から上記再試行を開始する。
- `shared/src/androidMain/kotlin/network/HttpClientFactory.android.kt:47` とiOS counterpart: 通信層も5xx・対象例外に最大2回の再試行を行う。
- `shared/src/commonMain/kotlin/ui/image/ImageLoaderProvider.kt:501`: `/src/` の失敗では拡張子の別候補を順番に試す。互換表示では最大5候補、動画候補は無効。あぷ系URLには除外もある。

今回の7.3秒では本文側の再試行まで確認できた。通信層の再試行や拡張子探索が実際に発生した証拠はない。失敗時の待ち時間を画像単位の総時間で制御する仕組みは、個々のタイムアウトだけの場合より予測しやすい。

### 2. 長い本文で先回りして画像を確保する専用処理がない

`CompatibilityApp.kt:8027` の `LazyColumn` / `itemsIndexed` から各投稿画像をCompose・Coilに渡す。本文の次の数画像を明示的にネットワーク先読みする処理はこの経路にない。LazyColumnの項目プリフェッチはあり得るが、画像の読込完了を保証するものではない。初めて表示する画像はスクロール時に読込待ちになり得る。

ネットワーク失敗・再試行状態は投稿Composableの `remember` にあり、長いスレッドで項目が破棄・再生成されるとその状態が維持される保証もない。ただし、今回の失敗を項目キャンセルが引き起こした証拠は得ていない。

### 3. 並列数の設定は通常時のHTTP同時接続数の厳密な上限ではない

`AppDispatchers.kt:67` は `limitedParallelism` による実行並列度の制御。サスペンド中の全通信を数えるSemaphoreではない。`ImageMemoryPressure.kt:239` のリクエストゲートは通常メモリ状態では迂回される。このため設定の「6」をHTTP通信が常に6本以下という意味には解釈できない。画像専用の可視項目優先・通信中リクエスト数の計測が必要。

### 4. メモリ圧迫後はキャッシュ縮小と直列化が起き得る

`ImageLoaderProvider.kt:338` と `ImageMemoryPressure.kt` により、OSのメモリ圧迫通知でキャッシュと並列度を減らす。重い状態では1本になり、通常への回復待ちは30秒または60秒。Androidでは `TRIM_MEMORY_UI_HIDDEN` もMODERATEに分類する。

画像の多いスレッドやアプリ復帰後の一時的な遅さを説明し得る経路だが、今回の計測でこのゲートが発動した証拠はない。実測した長いスレッドのPSSは約291MiB。GCの総時間と停止時間は別で、ログの100ms程度のGC総時間をそのままUI停止時間と見なしてはいけない。

### 5. 特定画像の手動再読込後はキャッシュ無効が残る

`CompatibilityApp.kt:9063` で投稿別の再読込トークンを保持し、`:11606` で非0の間はメモリ・ディスク両キャッシュを無効にする。成功時にこのトークンを戻す処理は見当たらない。同じスレッド内で再スクロールすると再取得しやすい条件になる。今回はこの操作をしていないので再現原因には含めない。

### 6. ビューアーの先読みは本文の遅延とは別件

`CompatibilitySecondaryScreens.kt:4967` の先読みは通常 `resolveCompatPostPreviewUrl` を使うため、サムネイルがある画像では次の原寸画像を取得しない。一方、表示本体は `:5788` の `Size.ORIGINAL` を待ち、サムネイルは失敗時のみ表示する。画像を送る際の待ち時間には影響し得るが、今回ユーザーが補足した長いスレッド本文の主要な説明としては扱わない。

## 改善・追加計測の優先順位

1. 画像ごとの開始・成功・失敗・キャンセル、例外種別、HTTPステータス、取得元（メモリ・ディスク・通信）、各段階の時間を計測する。今回の約4.9秒の最初の失敗を分類するのが最優先。
2. 本文の可視画像を優先し、直近の少数画像のみ先読みする。画面外の古いリクエストと失敗再試行が可視画像を待たせないようにする。
3. 通信層とUI層の再試行を画像単位で把握し、重複した待ち時間を制御する。404等の確定失敗と一時失敗を区別する。
4. 手動再読込後のキャッシュ無効を1回の試行に限定することを検討する。

この調査では製品コードを変更していない。単なる並列数増加は、通信・メモリ負荷を増やす可能性があるため、原因確定前の対処としては採用していない。
